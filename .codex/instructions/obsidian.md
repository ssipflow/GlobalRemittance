# 옵시디언 문서화 워크플로우

## 범위와 기록 기준

개발 목표, 결정 근거, 검증 결과를 사람이 읽고 다음 작업에 사용할 수 있게 남긴다.
프로젝트 폴더만 대상으로 `scripts/obsidian_sync.py`의 명시적 단방향 동기화를 사용한다.
연결 방법과 명령은 `docs/harness/obsidian.md`를 따른다. 개인 경로는 `.harness/obsidian.json`에만 둔다.
최초 실제 기록 전에 사용자가 지정한 Vault와 프로젝트 폴더를 확인한다.
그 전에는 저장소 작업 기록에 요약을 남기고 옵시디언 반영은 미설정으로 표시한다.
플러그인 설치, Vault 전체 탐색, 감시 프로세스, 양방향 동기화와 Vault Git 작업은 실행하지 않는다.

코드/Git/PR 상태는 실제 저장소와 GitHub가 기준이다. state.md는 현재 상태와 다음
행동, 작업별 기록은 실행 근거, docs/decisions는 중요한 설계 선택의 원본이다.
옵시디언은 이해를 위한 요약과 원본 링크를 제공하며 별도의 에이전트 정책 원본으로
사용하지 않는다. 새 개발 목표가 확정되면 개요에 목표·범위·완료 기준을 적는다.
과거 목표는 이력으로 보존하고 미확정 계획을 확정 사실로 기록하지 않는다.

## 단계

1. 시작: 관련 개요·작업 노트·결정만 읽고 코드/Git과 대조한다. 작업 ID, 목표,
   범위, 완료 기준, 브랜치, 관련 링크를 작업 노트에 기록한다.
2. 진행: 중요한 결정은 문제, 고려한 대안, 선택 이유, 비용과 원본 결정 링크를
   남긴다. 전체 대화와 도구 로그를 그대로 옮기지 않는다.
3. 검증: 실제 실행 명령, 결과, 검증한 snapshot/커밋을 기록한다. 실패·건너뜀·
   미확인을 성공과 구분하고 남은 문제와 다음 행동을 남긴다.
4. 커밋 전: 저장소 기억과 노트 초안을 갱신하고 변경 전체를 내부 리뷰·검증한다.
   외부 Vault 쓰기는 저장소 snapshot 게이트의 검증 대상이 아니므로 별도로 읽어 확인한다.
5. PR 생성 후: 실제 URL과 HEAD를 확인해 옵시디언 노트에 연결한다. PR 생성은
   작업 전달 완료이며 승인·병합 완료가 아니다. 이 단계에서 커밋한 저장소 기억을
   다시 수정하지 않는다. 승인·병합은 사람이 한다.
6. 중단·재개: 마지막 검증 상태, 장애물, 다음 행동을 남기고 재개 시 원본과 대조한다.
   사람의 병합 사실은 다음 세션에서 실제 상태를 확인한 뒤 반영한다.

## 노트와 갱신

프로젝트 폴더 아래 `프로젝트 개요.md`, `작업/<작업 ID>.md`, `결정/<결정 ID>.md`를
기본 제안으로 사용하되 기존 Vault 구조가 있으면 따른다. 작업 노트 항목은 목표/범위,
상태, 브랜치, 변경 요약, 결정 링크, 검증 근거, 커밋/PR 링크, 남은 문제, 다음 행동이다.
노트 간에는 [[노트 이름]] 링크를 쓰고 저장소 원본은 GitHub 파일/커밋 링크로 연결한다.

같은 작업 ID 노트를 갱신해 재시도 시 중복을 만들지 않는다. 사용자 내용을 보존하고
에이전트 담당 구역만 수정한다. 담당 구역을 구분할 수 없으면 별도 작업 노트를 연결한다.
기록 후 다시 읽어 내용과 링크를 확인한다. 비밀 값, 개인정보, 전체 대화, 토큰과 민감한
로컬 경로를 기록하지 않는다. 접근 실패는 문서화 미반영으로 보고하고 저장소 작업
기록에 다음 행동을 남긴다. 커밋 후 실패는 무시되는 로컬 보고서에 기록하고 다음 작업에서
저장소 기억에 반영한다. 이미 생성한 커밋/PR을 취소하거나 중복 생성하지 않는다.

## 실행과 권한

작업 시작·중단·커밋 전에는 dry-run으로 대상을 확인하고 sync한다. PR 생성 후에는
하네스가 확인한 PR URL/HEAD를 노트에 반영한다. 외부 쓰기 승인은 프로젝트 폴더만
대상으로 요청한다. CLI의 경로 검사는 스크립트 범위 제한이며 OS 차원의 Vault 읽기
격리를 보장하지 않는다. 별도 권한 프로필을 적용하지 않았다면 엄격한 접근 격리가
완성됐다고 보고하지 않는다. sync 결과와 읽기 확인을 로컬 보고서로 확인한다.
