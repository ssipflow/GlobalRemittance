# 대표 개선 사례

현재 문서의 기준 구현은 `dev 69d2138`(PR #58 반영)이다. 아래 수치는 연결된 과거 작업의 관찰값이며 이 문서 작성 중 새로 측정한 결과가 아니다. AI와 사람의 역할은 [개발 절차](ax-workflow.md)에 구분했다.

## 1. DB 무응답과 타임아웃

**문제와 가정.** DB 연결 획득 제한을 설정해도, 이미 풀에서 얻은 연결로 보낸 쿼리는 별개의 대기다. PostgreSQL 컨테이너를 pause해 연결을 유지한 채 응답을 멈추자 connection-timeout 2초와 무관하게 요청이 6초 관찰 동안 끝나지 않았다. unpause 직후에야 200으로 끝났다. 6초는 최대 대기 시간이 아니라 관찰 창이다.

**선택.** Coordinator가 PostgreSQL JDBC `socketTimeout` 도입을 결정했다. 기본값은 60초이고 잠금 대기 한도보다 커야 한다. 설정 검증기는 잘못된 형식·범위·잠금 대기 이하 값을 DB 연결 전에 거부한다. 연결 획득 제한을 더 줄여도 이미 얻은 연결의 읽기 대기는 해결되지 않는다. 이 변경은 서버 자동 재시도나 요청 전체 deadline을 도입하지 않는다.

**검증.** 소켓 타임아웃 4초·잠금 대기 1초인 테스트에서 풀 연결 요청은 약 4031ms 후 503 `DB_UNAVAILABLE`로 끝났다. 새 연결 요청은 약 2초 후 503이었다. pause 해제 후 풀 active 0과 복구를 확인했고, 같은 키 재시도 뒤 접수·키는 1회이며 부분 상태가 없었다. 후속 Toxiproxy 테스트로 블랙홀·리셋·지연도 확인했다.

**한계.** pause는 네트워크 단절 자체가 아니다. 소켓 타임아웃은 읽기 단위여서 응답 읽기마다 1초 지연을 주면 전체 요청이 약 6초가 될 수 있다. HTTP 전체 시간을 4초로 보장하지 않는다. 운영 기본 60초의 응답시간을 테스트 4초 관찰값으로 주장할 수 없다.

근거: [작업 기록](../harness/tasks/postgres-failure-modes.md), [설계 결정](../decisions/db-socket-timeout.md), [장애 테스트](../../src/test/java/com/nelson/remittance/postgres/PostgresFailureModesTest.java), [네트워크 실험](../harness/tasks/network-partition.md).

## 2. 커밋 응답 유실과 멱등성

**문제.** DB는 커밋했지만 앱은 성공 응답을 못 받을 수 있다. 503을 받았다고 미접수로 판단해 새 요청을 만들면 중복 위험이 있다. 단순 연결 종료나 응답 방향 블랙홀만으로 커밋 뒤 유실을 재현했다고 볼 수도 없다.

**재현과 선택.** 테스트용 TCP 프록시가 PostgreSQL COMMIT 메시지를 식별해 딱 한 번 결함을 주입한다. COMMIT을 DB에 전달하기 전에 버리는 경우와, 서버 커밋 후 응답을 폐기하고 연결을 리셋하는 경우를 분리했다. 시간 지연이나 우연한 경쟁에 의존하지 않고 주입 횟수도 단언한다. main 코드는 바꾸지 않고 기존 사용자 행 잠금·키 귀속·트랜잭션 설계를 검증했다.

| 주입 지점 | 최초 응답과 DB 상태 | 같은 키 재시도 |
| --- | --- | --- |
| COMMIT이 DB에 도착하기 전 | 503, 접수 0행·한도 합계 0 | 200, 접수 1행 |
| DB 커밋 후 성공 응답 유실 | 503, 해당 키 접수 1행이 이미 반영됨 | 정상 성공과 같은 200 본문, 행 수·한도 합계 불변 |

**확인한 것.** 과거 기록상 3회 반복 통과했다. HTTP 응답뿐 아니라 별도 DB 조회로 접수 행·키 행·합계를 확인하고 이력의 오늘 건수와 대조했다. 응답 유실 자체를 없앤 결과가 아니라, 같은 키 재시도로 중복 효과를 막는 결과다.

**한계.** 프록시의 한 COMMIT 지점에 주입한 TCP 리셋이다. 별도 호스트 장애나 모든 패킷 손실 형태의 검증은 아니다. 성공 응답 재현은 접수 후 24시간 미만이며 실패 응답은 저장하지 않는다. 처음부터 키 없이 보낸 요청은 이 보장을 받지 못한다.

근거: [작업 기록](../harness/tasks/commit-response-loss.md), [테스트와 프록시](../../src/test/java/com/nelson/remittance/postgres/PostgresCommitResponseLossTest.java), [멱등성 설계](../application/design.md).

## 3. 하네스의 소유 범위 변경

**문제.** 작업 중 필요한 파일이 늘어나면 `finish`가 소유 범위 밖 변경을 거부했다. 이전 세 작업에서는 추가 명령이 없어 `.harness/task.json`을 수동 편집했다. 제한을 우회하는 수동 편집은 실수하기 쉽고 추가 내역도 남지 않았다.

**선택.** 사용자가 개선 진행을 승인했고, 활성 작업에 `own --files ...`를 추가했다. `begin`과 경로 검증을 공유해 개별 상대 경로만 받으며 디렉터리·절대 경로·상위 경로·내부 상태를 거부한다. 추가 파일과 시각을 `ownership_additions`에 기록한다. 기존 소유 범위 제한을 없애는 대신 범위 변경을 명시적인 동작으로 만들었다.

**검증.** 추가 파일의 커밋 포함, 추가 내역, 잘못된 경로 거부 후 목록 보존, 활성 작업이 없거나 커밋 후에는 거부함을 테스트했다. `own` 자체는 파일 내용을 바꾸지 않아 기존 snapshot 근거를 유지하지만, 파일이 이후 바뀌면 오래된 리뷰·검증으로 커밋할 수 없다.

**한계.** 추가 이유를 강제하지 않고 기록은 Git 미추적 로컬 상태에만 남는다. 이미 수정된 파일도 등록할 수 있어 사용자의 기존 변경 배제는 Coordinator 책임이다. 하네스는 절차를 돕지만 범위 확장이 적절한지 자동 판단하지 않는다.
