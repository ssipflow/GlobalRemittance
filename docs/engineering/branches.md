# 브랜치와 승격 정책

실제 운영/테스트 서버는 없다. main은 운영 배포 원본, test는 테스트 서버 배포
원본이라고 가정한다. 이 정책을 위해 CI/CD나 서버를 새로 구축하지 않는다.

| 브랜치 | 역할 | 변경 반영 |
| --- | --- | --- |
| `main` | 운영 기준 | 검증한 dev에서 PR을 통해 반영 |
| `dev` | 검증한 기능의 통합 기준, 작업 분기 원본 | test 검증을 통과한 작업 브랜치를 병합 |
| `test` | 테스트 서버 배포와 통합 검증 가정 | feature/hotfix를 병합하고 후보 검증 |
| `feature/<feature-name>` | 기능·리팩터링·문서·하네스 작업 | dev에서 분기, 작업 커밋 |
| `hotfix/<fix-name>` | 이 프로젝트의 긴급 수정 | 사용자 지정 흐름대로 dev에서 분기, 동일한 검증/승격 |

작업 이름은 소문자 영문·숫자와 하이픈을 사용한다.
예: `feature/test-isolation`, `feature/remittance-domain`, `hotfix/quote-expiry`.
main/dev/test에는 일반 구현 커밋을 직접 만들지 않는다.

## 정상 흐름

1. 깨끗한 dev에서 작업 브랜치를 생성한다.
2. 작업 브랜치에서 구현 → 독립 리뷰 → 자동 검증 → 수정 → 작업 기억 → 커밋을 수행한다.
3. 해당 작업 브랜치를 test에 병합한다. test HEAD와 작업 브랜치 SHA,
   검증 명령/결과를 기록한다. 서버가 없으므로 로컬 통합 검증으로 테스트를 대체한다.
4. test에서 통과한 **같은 작업 브랜치 SHA**를 dev에 병합한다.
   test 브랜치 전체를 dev에 병합하지 않는다. 다른 미검증 후보가 섞일 수 있기 때문이다.
5. dev의 통합 결과를 다시 검증한다. dev → main PR에 포함되는 모든 작업의
   test 검증 근거, 최종 dev SHA, 완료 기준과 미해결 사항을 확인한다.
6. dev → main PR의 리뷰/검증을 통과하면 main에 병합하는 것을 운영 승격으로 간주한다.

test에서 수정이 필요하면 작업 브랜치에서 수정하고 다시 test에 병합/검증한다.
검증 후 작업 브랜치가 바뀌면 기존 승인은 유효하지 않다.
test 병합 시에만 해결한 충돌은 dev에서 사라질 수 있으므로, 해결 내용을 작업 브랜치에
반영하고 새 SHA를 test에서 다시 검증한다. dev 병합에서 새 충돌 해결/행동 변경이
생기면 그 통합 결과 역시 test에서 검증한 뒤 main 후보로 삼는다.

## 릴리스와 실행 범위

여러 작업을 승격할 때는 dev → main의 전체 diff가 릴리스 후보가 된다.
테스트하지 않은 작업이 포함되면 승격하지 않는다. PR 준비 이후 dev가 바뀌면
새 HEAD에서 검증과 리뷰를 다시 수행한다. PR 본문에 검증한 SHA를 기록한다.
작업 병합은 `--no-ff`로 출처를 남기고, 작업 브랜치는 승격이 끝날 때까지 보존한다.
실제 원격 PR은 원격 push와 PR 생성이 요청된 릴리스 작업에서 만든다.

현재 하네스가 자동으로 하는 일은 작업 브랜치에서의 검증과 로컬 커밋이다.
test/dev/main 병합, push, PR 생성은 별도 승격 작업으로 수행하고 결과를 기록한다.
하네스는 begin에서 이름/dev 계보를 확인하고, 실행 중 브랜치 변경을 거부한다.
원격 branch protection이나 직접 git commit/merge까지 강제하는 장치는 아니다.
