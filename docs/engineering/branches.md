# 브랜치와 승격 정책

실제 운영/테스트 서버는 없다. main은 운영 배포 원본, test는 테스트 서버 배포 원본이라는 가정이다. 이 정책을 위해 CI/CD나 서버를 새로 구축하지 않는다. 에이전트의 최신 실행 범위는 [workflow](../../.codex/instructions/workflow.md)를 따른다.

| 브랜치 | 역할 | 변경 반영 |
| --- | --- | --- |
| `main` | 운영 기준이라는 가정 | 검증한 dev에서 PR, 사람 승인·병합 |
| `dev` | 검증한 기능의 통합 기준, 작업 분기 원본 | 작업 브랜치의 PR, 사람 승인·병합 |
| `test` | 테스트 배포 원본이라는 의미상 브랜치 | 사람의 별도 요청 없이 병합하지 않음 |
| `feature/<feature-name>` | 기능·리팩터링·문서·하네스 작업 | dev에서 분기, 검증·커밋·push·dev PR |
| `hotfix/<fix-name>` | 긴급 수정 | dev에서 분기, 같은 검증·PR 절차 |

작업 이름은 소문자 영문·숫자와 하이픈을 사용한다. 예: `feature/test-isolation`, `hotfix/quote-expiry`. main/dev/test에는 직접 구현 커밋·병합·push하지 않는다.

## 일반 작업의 흐름

1. Git 상태를 확인하고 깨끗한 dev에서 작업 브랜치를 생성한다. 사용자 변경이 있으면 별도 작업 트리를 사용한다.
2. `begin`에 소유 파일·완료 기준·검증 명령을 등록하고 구현 → 내부 독립 리뷰·검증 → 필요한 수정을 수행한다.
3. 작업 기억을 포함한 최종 snapshot을 리뷰·검증하고 `finish`로 로컬 커밋한다.
4. `publish`로 작업 브랜치만 push하고 dev 대상 PR을 생성한다. 실제 PR URL을 확인하면 일반 작업이 완료된다.
5. GitHub AI가 PR 리뷰·코멘트를 담당하고 사람이 최종 승인·병합한다. 에이전트는 리뷰 게시·approve·merge·auto-merge를 수행하지 않는다.

커밋 후 파일 수정이 필요하면 `reopen` 후 내부 리뷰·검증과 후속 커밋을 거친다. 기존 이력을 재작성하지 않는다. committed 작업은 `finish`를 반복하지 않고 `publish`를 수행한다. 실패하면 상태를 확인해 재시도한다.

## 승격과 강제 범위

일반 작업은 test 병합이나 dev → main 승격을 실행하지 않는다. dev → main도 사람이 최종 승인·병합할 PR로 전달한다. 별도 승격 요청이 있으면 통합 후보 전체 diff와 최신 HEAD를 검증하고 근거·미해결 사항을 기록한다. 검증 뒤 후보가 바뀌면 이전 통과를 그대로 사용하지 않는다.

하네스는 `begin`에서 브랜치 이름과 로컬 dev 계보를 확인하고 실행 중 브랜치 변경을 거부한다. `publish`는 origin과 지정 저장소를 확인해 작업 브랜치만 push한다. 원격 branch protection이나 직접 Git 명령을 막는 보안 경계는 아니다. PR만 사용한다는 지침이 서버 측 직접 push 차단을 뜻하지 않는다.
