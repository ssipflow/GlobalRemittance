# 프로젝트 공통 원칙

변경 빈도: 낮음. 프로젝트 목표, 아키텍처, 품질과 작업 절차의 기준이다.
원칙을 바꾸려면 명시적인 요구 변경과 이유를 작업 기록에 남긴다.
개인 작업 선호는 `preferences.md`에서 관리한다.

## 목표와 아키텍처

GlobalRemittance를 정확성, 재현성, 유지보수성, 설명 가능한 설계를 갖춘
포트폴리오로 개선한다. 기본 컨벤션은 클린 아키텍처다.
의존성은 외부 기술에서 내부 정책으로 향한다:

```text
adapter (web, persistence, forex) → application (use case, port) → domain
bootstrap/config → 각 계층의 객체 조립
```

- `domain`: 송금 금액, 통화, 수수료, 견적 만료, 한도 등의 업무 규칙과 상태.
  Spring, JPA, HTTP, JWT 구현, 외부 API에 의존하지 않는 Java 코드로 작성한다.
- `application`: 사용 사례의 실행 순서와 입출력 포트. 도메인과 포트에 의존하며
  Repository/외부 API 구현을 직접 참조하지 않는다. 시간은 주입 가능한 경계로 다룬다.
- `adapter.in`: HTTP 입력 검증, 인증된 사용자 식별, 사용 사례 호출, 응답 변환.
  컨트롤러에 업무 규칙을 구현하지 않는다.
- `adapter.out`: 영속성, QueryDSL, 환율 API, 암호화 구현. application이 정의한
  포트를 구현하고 JPA 모델과 도메인 모델의 변환을 책임진다.
- `bootstrap/config`: DI, 설정, 트랜잭션 경계 등 기술적인 조립.
  트랜잭션은 사용 사례 단위의 원자성을 유지하도록 외부에서 구성한다.
- 계층 경계를 넘어 JPA entity나 웹 DTO를 내부 정책으로 전달하지 않는다.
  인터페이스는 실제 경계를 위해 도입하며 DTO마다 기계적으로 만들지 않는다.

이것은 목표 구조다. 현재 controller/service/repository 구조가 이 기준을
이미 충족한다고 간주하지 않는다. 기능 단위로 점진적으로 이전하고,
기존 API 계약과 동작을 회귀 검증한다. 패키지 이름만 바꾸는 작업으로 끝내지 않는다.

## 품질 기준

- 금액 연산의 정밀도, 반올림 기준, 동시성, 중복 접수, 일일 한도,
  견적 만료와 시간 경계, 인증과 소유권을 우선 검증한다.
- 도메인 테스트는 프레임워크 없이 실행 가능하게 만들고, 어댑터는 필요한
  통합 테스트로 검증한다. 테스트는 사용자 홈 DB와 실제 환율 API에서 격리한다.
- 검증 실패를 무시하거나 테스트를 약화해 통과시키지 않는다.
- 설계 선택의 배경과 비용을 기록하며, 필요 이상의 추상화나 인프라를 추가하지 않는다.
- 비밀 값과 개인정보를 코드, 로그, 에이전트 기억에 저장하지 않는다.

## 에이전트 작업 계약

- Coordinator가 작업 범위와 완료 기준을 정하고 구현·독립 리뷰·검증을 조정한다.
- 쓰기 소유자는 한 명으로 유지한다. 자식 에이전트는 커밋하지 않는다.
- 최신 변경의 독립 리뷰와 실제 검증을 통과하고 작업 기억을 갱신해야 자동 커밋한다.
- 등록한 작업 파일만 커밋하며 기존 사용자 변경을 포함하지 않는다.
- 작업과 커밋은 `branches.md`에 정한 작업 브랜치에서 수행한다.
- 자동 로컬 커밋까지가 기본 실행 범위다. 배포 가정은 CI/CD 구축 요청이 아니다.
  브랜치 승격, 원격 push와 실제 PR 생성은 해당 작업의 명시적인 요청에 따라 수행한다.
- 맥락은 state/backlog/작업 기록/설계 결정으로 복원하고 관련 파일만 읽는다.

## 지침 적용 순서

현재 사용자의 명시적인 요청을 우선한다. 저장소 내부 지침 간에는
공통 원칙과 브랜치 정책을 품질/절차 기준으로, 개인 선호를 그 범위 안의
진행·소통 방식으로 적용한다. 개인 선호만으로 검증이나 브랜치 규칙을 완화하지 않는다.
원칙 변경이 필요한 요청은 공통 지침도 갱신하여 기록과 실제 동작을 일치시킨다.
