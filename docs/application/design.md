# 주요 설계

## 금액과 환율

double 오차를 피하기 위해 BigDecimal을 사용한다. 모든 반올림은 HALF_UP이며 Java Currency 기준 KRW·JPY는 0자리, USD는 2자리다. 환율은 대상 통화 1단위당 KRW이며 12자리로 반올림한다.

| 통화·원화 금액 | 고정 수수료 | 비율 |
| --- | --- | --- |
| USD 100만원 이하 | 1000원 | 0.002 |
| USD 100만원 초과 | 3000원 | 0.001 |
| JPY | 3000원 | 0.05 |

입력 원화를 먼저 정수화한 후 수수료 구간을 선택한다. 비율 수수료를 원화로 반올림하고 고정 수수료를 더한다. 수취금액 = (원화 금액 − 수수료) ÷ 수취통화 환율이다. 일일 한도용 USD 역시 순송금 원화를 USD 환율로 나눈다.

수수료 차감 후 0은 허용하며 음수는 거부한다. 입력·계산 결과가 DECIMAL(22,12)의 범위를 넘으면 저장 전에 INVALID_REQUEST로 거부한다. 원 요구사항의 JPY 소수 예시는 명시된 통화 자릿수 규칙보다 우선하지 않는다.

## 견적을 감사 기록으로 저장

견적 시점의 환율·수수료·순송금 USD를 고정해 접수 시 재계산하지 않는다. 나중의 환율 변화로 접수 금액이나 일일 한도가 바뀌지 않으며 이력에서 계산 근거를 설명할 수 있다. Quote는 불변 모델이고 접수 상태 변경은 새 값을 만든다.

## 한도와 동시성

개인은 KST 하루 1000 USD, 법인은 5000 USD다. 견적별 USD 2자리 반올림 값을 합산하며 한도와 같으면 허용한다. 접수 시 사용자 DB 행을 비관적 잠금으로 잡고 합계 조회·한도 검사·접수를 같은 트랜잭션에서 실행한다.

견적만 잠그면 서로 다른 두 견적이 동시에 기존 합계를 보고 한도를 초과할 수 있다. 사용자 잠금은 이 경쟁을 막지만 같은 사용자의 접수와 이력 조회를 직렬화하는 비용이 있다. 중복 접수 역시 잠금 안에서 requestedTime을 확인해 한 번만 수락한다.

## 시간과 경계

Clock을 주입해 테스트에서 시간을 고정한다. JWT는 30분, 견적은 10분이며 정확한 만료 순간부터 거부한다. 저장은 UTC Instant, 하루 판정과 API 표시는 Asia/Seoul이다. 서버 기본 시간대에 일일 한도 정책을 맡기지 않는다.

## 인증과 개인정보

비밀번호는 BCrypt로 해시하며 UTF-8 72바이트 초과를 거부해 묵시적 잘림을 막는다. 식별번호는 랜덤 nonce를 사용하는 AES-GCM으로 암호화하고 무결성도 검증한다. 저장 길이를 위해 UTF-8 64바이트 제한을 둔다. 실행 키가 없거나 잘못되면 시작을 거부한다.

JWT의 서명·만료를 확인한 인증 사용자를 기준으로 견적 소유권을 판단한다. 회원/로그인 DTO의 toString을 가리고 API 내부 오류에 원시 예외를 노출하지 않는다. H2 유일 제약 오류에 이메일이 포함될 수 있어 SqlExceptionHelper 원시 로그를 차단했다. 그 비용으로 DB 진단 상세가 줄어들며 운영에서는 개인정보를 제거한 관측 체계가 필요하다.

## 포트와 테스트

업무 규칙은 프레임워크 없는 domain, 실행 순서는 application에 둔다. DB·암호화·환율·시간 경계를 대체 가능하게 하면서 DTO마다 기계적인 인터페이스를 만들지 않는다.

도메인·보안 테스트와 H2/API 통합 테스트로 반올림·수수료 경계·만료·KST 자정·개인/법인 한도·소유권·중복 및 동시 접수를 검증한다. ArchitectureTest는 내부 계층 의존성을 검사한다. Spotless와 Checkstyle은 Gradle check에 연결한다.

## 남은 비용과 한계

- 환율은 ConfiguredRates의 예시 값이며 실제 시세 연동은 없다. 외부 공급처는 Rates 포트 구현으로 교체한다.
- 전체 이력을 메모리에서 집계하므로 거래량 증가 시 DB 집계와 페이지네이션이 필요하다.
- embedded H2 검증은 운영 DB의 잠금·복구·장애 검증을 대신하지 않는다.
- 실제 금융기관 송금과 데이터 마이그레이션은 제공하지 않는다.
