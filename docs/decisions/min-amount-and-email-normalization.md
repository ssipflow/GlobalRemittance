# 최소 금액 5000 KRW와 이메일 대소문자 정규화

- 상태: 사용자 결정(확정). 요구사항 원본(`docs/requirements/project-goals.md`)은 수정하지 않았고, 아래 두 정책은 원본에 없는 추가 규칙이다.

## 1. 최소 금액 5000 KRW

- 결정: 견적 요청 금액(KRW)을 HALF_UP으로 정수화한 값이 5000 미만이면 거절한다. 정확히 5000은 허용한다.
- 위치: 도메인 `QuotePolicy.calculate`. 양수가 아닌 입력(`NEGATIVE_NUMBER`)을 먼저 가르고, 저장 범위 검사 뒤에 비교한다.
- 오류 코드: 새 `ErrorCode.AMOUNT_TOO_SMALL`(HTTP 400)을 만들었다. 근거는 api.md 오류 계약이 코드마다 의미를 고정하고 있고
  `INVALID_REQUEST`는 형식·자릿수 오류, `NEGATIVE_NUMBER`는 부호·수수료 초과 의미라 재사용하면 클라이언트가 "금액이 작다"는 원인을
  구분할 수 없기 때문이다. 400 매핑은 ApiExceptionHandler의 기본 분기가 이미 처리하므로 핸들러 변경이 없다.
- DTO: `QuoteInput`은 정밀도·통화 형식만 검증하고 업무 하한은 도메인에 맡기는 구조라 Bean Validation 제약을 추가하지 않았다
  (소수 `4999.5`는 정수화하면 5000이라 DTO에서 `@DecimalMin`으로 자르면 도메인 규칙과 어긋난다).
- 5000원의 수취액: USD 순송금 3990원(수수료 1000+10), JPY 1750원(3000+250). 수취액이 0보다 큰 조건은 USD 환율 798000 미만,
  JPY 환율 3500 이하다. 설정·시뮬레이션 환율 범위에서는 항상 양수이며(QuotePolicyTest, RemittanceApiTest로 확인), 극단 환율에서는 0.00 반올림이 가능하지만 별도로 막지 않았다.
- 영향: 이전에 현재 동작으로 고정한 1003원(순송금 1원, 0.00 USD) 견적은 이제 거절된다. 관련 테스트를 새 정책으로 바꿨다. k6 부하 테스트의 금액(1만~3만 KRW)은 영향이 없다.
- 한도 테스트: 1센트 초과를 만들던 1012원 견적은 최소 금액 미만이라 5000원 견적(3.99 USD)으로 바꿨다. 1센트 경계 자체는 DomainRulesTest가 확인한다.

## 2. 이메일 대소문자 정규화

- 결정: userId는 가입·로그인 모두 소문자(`Locale.ROOT`)로 정규화하고 정규화된 값을 저장한다. 앞뒤 공백은 `@NotBlank @Email` 검증이 이미 거부하므로 trim하지 않는다.
- JWT `userId` 클레임은 저장된 정규화 값이다. 클레임 구성은 바꾸지 않았다(요구사항상 보류).
- 기존 데이터: Flyway V3(H2·PostgreSQL 각각)이 `user_id`를 소문자로 갱신한다. 정규화 후 중복이 생기면 합치지 않고 실패한다.
  - PostgreSQL: `DO` 블록이 `GROUP BY LOWER(user_id) HAVING COUNT(*) > 1`을 검사해 어떤 행도 바꾸기 전에 명시적 예외를 던진다(트랜잭션 DDL이라 부분 적용 없음).
  - H2: 절차 블록이 없어 UPDATE가 `uk_users_user_id` 유일 제약 위반(23505)으로 실패하며 메시지는 제약명이다. MigrationTest가 실패와 데이터 불변(2건 유지)을 확인한다.
  - 실패하면 운영자가 충돌 계정을 확인해 직접 정리한 뒤 재실행해야 한다.
- 한계: DB의 `LOWER`는 비 ASCII 문자에서 Java `Locale.ROOT` 소문자 변환과 다를 수 있다(PostgreSQL은 DB 로캘 의존). `@Email`이 허용하는 비 ASCII 입력의 예외 상황은 검증하지 않았다.
  `lower(user_id)` 함수형 유일 인덱스는 두지 않았다. 저장값이 항상 소문자이므로 기존 유일 제약이 동시 가입(PostgreSQL 6스레드 대소문자 변형 테스트)을 막는다.
  애플리케이션을 거치지 않고 DB에 대소문자 혼합 값을 직접 넣는 경우는 막지 않는다.
