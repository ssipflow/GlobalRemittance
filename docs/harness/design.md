# 포트폴리오 개선 하네스 설계

상태: Codex 에이전트 설정과 명령 훅 구현. 사용자가 새 세션에서 훅을 신뢰하면
작업 등록을 기반으로 실행한다. 사용법은 README.md를 따른다.

## 목표와 완료 기준

GlobalRemittance의 품질을 재현 가능한 검증과 설명 가능한 설계로 높인다.
Java 17, Spring Boot, JPA/QueryDSL 기반의 송금 서비스라는 현재 맥락을 유지한다.
품질은 추상화의 개수가 아니라 정확성, 테스트 재현성, 보안, 운영 가능성,
설계 근거와 실행 문서로 판단한다. 구체적인 결함은 초기 진단에서 확인한다.
안정적인 규칙은 `docs/engineering/principles.md`, 개인 선호는
`docs/engineering/preferences.md`로 분리한다. 클린 아키텍처를 목표로 점진적으로 이전한다.

## 역할

| 역할 | 책임 | 산출물 / 권한 |
| --- | --- | --- |
| Coordinator | 진단, 작업 분해, 완료 기준, 루프와 최종 통합 | 작업 계획, 상태 기록, 최종 커밋 담당 |
| Implementer | 작업 범위 안에서 코드와 회귀 테스트 개선 | 코드 수정; 동시 작업 시 파일 소유권 지정 |
| Reviewer | 변경과 주변 코드의 정확성, 보안, 도메인 규칙 검토 | 파일 위치, 재현 조건, 영향, 수정 제안; 읽기 전용 |
| Verifier | 실제 명령 실행, 회귀와 완료 기준 확인 | 실행 명령, 결과, 실패 원인; 검증 우회 금지 |

문서와 설계 결정은 Coordinator가 담당하며 필요할 때 전문 리뷰를 추가한다.
Reviewer와 Verifier는 독립적으로 병렬 실행할 수 있다.
여러 Implementer가 같은 파일을 동시에 수정하지 않는다.

## 실행 루프

1. 현재 Git 상태, 작업 기억, 관련 코드를 읽고 한 작업의 완료 기준을 정한다.
2. 변경 전 검증으로 기존 실패와 새 회귀를 구분한다.
3. Implementer가 코드와 필요한 회귀 테스트를 변경한다.
4. 변경 훅이 변경 파일과 diff 식별자를 수집하고 검토 필요 상태를 기록한다.
5. Coordinator가 Reviewer와 Verifier를 실행한다.
6. 근거 있는 결함을 수정한 후 수정된 diff에 대해 다시 검토하고 검증한다.
7. 작업 기억을 갱신한 최종 snapshot의 독립 리뷰·검증을 통과하고 완료 기준을 충족하며
   미해결 중대 결함이 없으면 해당 작업 파일만 스테이징하여 로컬 커밋한다.
8. 작업 브랜치만 push하고 dev PR을 생성해 실제 URL을 확인한다. 승인·병합은 사람이 맡는다.

훅은 이벤트와 검증 결과를 제공하고, 에이전트 실행과 재시도는 Coordinator가 관리한다.
파일 저장마다 에이전트를 중첩 호출하지 않는다. 작업 단위로 이벤트를 합치고
재진입 잠금을 둔다. 검토 후 변경이 생기면 기존 승인과 검증 결과를 무효화한다.
기본 수정 재시도는 작업당 3회이며 같은 실패가 반복되면 원인과 미해결 상태를 남긴다.
실패, 시간 초과, 검증 미실행 상태에서는 자동 커밋하지 않는다.
주관적인 스타일 제안은 완료 기준과 연결되지 않으면 새 작업으로 기록한다.

## 작업 기억

- `AGENTS.md`: 목표, 필수 실행 규칙, 기억 파일 위치만 간결하게 유지한다.
- `docs/harness/state.md`: 현재 작업, 완료 항목, 검증 상태, 장애물, 다음 행동.
- `docs/harness/backlog.md`: 우선순위, 근거, 작업별 완료 기준.
- `docs/decisions/`: 중요한 설계 결정의 배경, 선택, 대안과 비용.
- 작업별 기록: 변경 이유, 수정 파일, 검증 명령과 결과, 남은 문제와 커밋 식별자.

새 세션은 현재 상태와 해당 작업에 필요한 기록만 읽는다.
전체 대화나 모든 실행 로그를 상시 컨텍스트에 넣지 않는다.
작업 기록은 현재 코드와 Git 이력으로 대조한다. 비밀 값과 개인정보는 기록하지 않는다.

## 검증과 커밋 규칙

- 기본 앱 검증은 `./gradlew clean check bootJar --no-daemon`, Docker 기반 DB 검증은 `./gradlew postgresTest --rerun-tasks`로 분리한다.
  하네스 자체는 `python3 -m unittest discover -s scripts/tests -v`로 검증한다. 작업 범위에 맞는 명령을 등록한다.
- 테스트가 실제 DB, 사용자 홈 디렉터리, 외부 환율 API에 의존하는지 확인하고
  재현 가능한 테스트 환경을 먼저 확보한다.
- 송금 금액과 반올림, 일일 한도, 중복 접수와 동시성, 소유권과 인증,
  견적 만료와 날짜 경계를 도메인 리뷰의 주요 대상으로 삼는다.
- 현재 CI/CD는 없다. 로컬 등록 명령과 실제 결과를 근거로 삼으며 향후 CI를 붙이면 같은 완료 기준을 사용한다.
- 커밋은 Coordinator만 수행한다. 사용자 변경을 포함하지 않고 명시적인 파일 목록으로 스테이징한다.
- 커밋 직전 staged diff가 검토 및 검증한 변경과 같은지 확인한다.
- dev 기반 feature/hotfix에서만 작업한다. `finish` 이후 `publish`로 작업 브랜치 push·dev PR 생성까지 수행한다.
  test는 의미상 브랜치이며 일반 작업의 필수 병합 단계가 아니다.
- 내부 Reviewer는 읽기 전용이고 PR 리뷰·코멘트는 GitHub AI가 맡는다. 승인·병합은 사람의 책임이다.
  배포와 이력 재작성은 실행 범위에 포함하지 않는다. 세부 기준은 [브랜치 정책](../engineering/branches.md)을 따른다.

## 도입 순서

1. 실행 도구와 지원 훅 확인, 기존 빌드 및 테스트 진단.
2. 역할별 에이전트 설정, 짧은 AGENTS.md, 상태와 백로그 파일 작성.
3. 검증 스크립트와 변경/종료 훅, 재진입 방지와 반복 상한 구현.
4. 작은 개선 작업 하나로 실패 → 수정 → 재검증 → 기억 갱신 → 커밋을 검증.
5. 초기 진단 결과를 우선순위 백로그로 전환해 순차 개선.

## 자동 게이트의 한계

`attest-review`는 Coordinator가 독립 리뷰 결과를 확인해 기록하는 절차다. 하네스가 판단 품질이나 독립성을 인증하지 않는다. `own`은 활성 작업의 파일 범위를 명시적으로 추가하지만 기존 사용자 변경을 자동 구분하지 않는다. snapshot은 변경 이후 낡은 근거의 사용을 막으며 직접 Git 명령이나 동시 파일 수정을 차단하는 보안 경계는 아니다. 실제 사례는 [AX 개발 절차](../portfolio/ax-workflow.md)를 참고한다.
