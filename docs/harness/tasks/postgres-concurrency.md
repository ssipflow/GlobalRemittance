# postgres-concurrency

- 배경: 백로그 "운영 DB의 잠금·장애 복구 검증"의 2단계. PR #27이 PostgreSQL 실행 경로와 스키마를 만들었고, 이 작업은 핵심 주장
  (사용자 행 잠금으로 동시 접수를 직렬화해 일일 한도·중복·멱등성을 지킨다)을 실제 PostgreSQL 16에서 재현 검증한다.
- 사용자 결정: 2단계 진행. 범위는 1단계에서 예고한 대로(내가 제안, 사용자가 진행 요청).
- 계약(검증할 보장):
  1. 같은 견적 동시 접수는 정확히 1건 성공, 나머지 ALREADY_REQUESTED.
  2. 서로 다른 견적의 동시 접수가 합산 일일 한도(개인 1000 USD)를 넘지 않는다.
  3. 같은 Idempotency-Key·같은 견적의 동시 요청은 모두 200이되 효과는 1회. 같은 키·다른 견적은 1건만 성공하고 나머지 422.
  4. 잠금 대기 초과는 PostgreSQL SQLState 55P03을 거쳐 503 LOCK_TIMEOUT(`Retry-After: 1`)이 되고, 해제 후 같은 요청이 성공하며 부분 상태가 남지 않는다.
  5. 이력 조회는 사용자 행 잠금에 막히지 않는다.
  6. DB가 연결을 끊어도(`pg_terminate_backend`) 풀이 복구되어 이후 요청이 정상 처리되고 실패한 시도가 부분 상태를 남기지 않는다.
- 불변식: 기본(H2) 실행·API·오류 계약 불변. 기본 테스트 97개 유지. PostgreSQL 테스트는 태그 `postgres`로만 실행한다.
- 완료 기준: 위 시나리오의 `postgresTest` 통과(반복 실행으로 flaky 아님 확인), 기본 check·bootJar 통과, 문서의 "PostgreSQL 미검증" 서술을 검증 결과에 맞게 갱신.
  main 코드 결함이 드러나면 최소 수정하고 근거를 남긴다.
- 종료: 커밋·push·dev PR 후 옵시디언 sync. 승인·병합은 사람.

## 구현 결과와 직접 확인
- 구현: `PostgresConcurrencyTest`(태그 `postgres`, 8개). main 코드 동작 변경 없음(주석 2곳만: JpaStore, application.yaml — 낡은 "H2 URL만" 설명을 postgres 프로파일 포함으로 정정. 소규모라 Coordinator가 직접 수정).
- 시나리오: 같은 견적 6스레드(1건 성공·409), 한도 초과 견적 6개(2건 성공·4건 400 `LIMIT_EXCESS`, 합계 796.4), 같은 키·같은 견적(모두 200·효과 1회), 같은 키·다른 견적(1건·422),
  외부 연결 `FOR UPDATE` 중 접수(503 `LOCK_TIMEOUT`·`Retry-After: 1`·약 2.03초, 해제 후 200, 부분 상태 없음), PostgreSQL이 `55P03`을 내는지 직접 확인, 잠금 중 이력 조회(1초 미만 200),
  `pg_terminate_backend`로 모든 연결을 끊은 뒤 복구(관찰: 첫 요청 500, 두 번째 200; 재시도 상한 10회).
- 검증: `postgresTest` 14개(1단계 6 + 이번 8) 통과·실패 0·건너뜀 0, implementer가 `--rerun-tasks`로 반복 실행(최초 3회, 보강 후 2회)해 매번 통과. 기본 `check` 97개 유지.
- 독립 리뷰: 차단 결함 없음. 제안(55P03 직접 단언, 재시도 10회, 409/400 상태 단언, 스타일 정리, 문서의 "55P03 확인" 표현 완화)을 반영했고 반영분은 `verify`로만 확인했다.
- 한계/발견: 연결이 끊긴 직후 첫 요청은 500(`UNKNOWN_ERROR`)이다(풀이 끊긴 연결을 사용 시점에 알게 됨). 재시도로 복구되고 부분 상태는 없다. 이를 줄이는 풀 설정·재시도는 이번 범위 밖이다.
  다중 앱 인스턴스, 고부하·장시간 경쟁, DB 재시작·네트워크 분리, 롤백 실패 주입, 다른 PostgreSQL 버전은 검증하지 않았다. 앱 경로의 503이 어느 매핑 분기(JPA 예외/SQLState)로 변환됐는지는 구분하지 않았다.
