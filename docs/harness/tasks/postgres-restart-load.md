# postgres-restart-load

- 배경: 백로그 "운영 DB 검증"의 마지막 항목 "DB 재시작·고부하". 앞선 단계(동시성·롤백 실패·장애 503·다중 인스턴스)는 연결 단절(`pg_terminate_backend`)과
  중간 규모 경쟁까지 확인했다. 이 작업은 PostgreSQL 컨테이너를 실제로 재시작하는 동안의 응답 계약과 자가 복구,
  풀 크기를 넘는 폭주에서의 한도·중복·불변식을 실제 HTTP로 검증한다.
- 계약(검증할 보장):
  1. 재시작 중·직후 요청은 500이 아니라 성공(200) 또는 `Retry-After: 1`의 503 `DB_UNAVAILABLE`뿐이다.
  2. DB가 다시 준비되면 앱이 설정 변경·재기동 없이 스스로 복구해 정상 응답한다(재시작 명령 완료 이후 이력 조회·접수가 모두 200인 반복을 상한 90초 폴링으로 확인, 고정 sleep 금지).
  3. 재시작 중 실패한 접수는 부분 상태(requested_time만 또는 키만 있는 행)를 남기지 않고, 같은 키 재시도는 효과 1회다.
  4. 재시작 전에 성공한 접수는 보존되고 같은 키 재요청은 같은 응답을 재현한다.
  5. 폭주(풀 3개, 32스레드, 8사용자×16견적×2회)에서도 응답은 200 또는 정의된 오류(400 `LIMIT_EXCESS`, 409 `ALREADY_REQUESTED`, 503)뿐이고 500이 없다.
     사용자별 일일 합계(usd_amount)는 1000 이하이며 한도가 채워지고, 키 중복이 없고, 200 응답 수와 DB 접수 행 수가 사용자별로 일치한다.
  6. 풀을 고갈시키면 요청은 connection-timeout 뒤 503 `DB_UNAVAILABLE`로 끝나 무한 대기하지 않고, 연결이 돌아오면 같은 요청이 성공한다.
- 불변식: main 코드·API·오류 계약 불변(결함이 드러나지 않았다). 기본(H2) 테스트 불변. PostgreSQL 테스트는 태그 `postgres`로만 실행한다.
- 재시작 시 포트 문제: Testcontainers 기본 매핑(임시 포트)은 `docker restart` 후 바뀔 수 있어, 컨테이너 생성 시 `withCreateContainerCmdModifier`로
  빈 호스트 포트를 고정 바인딩하고 시작 직후·재시작 후 `getMappedPort`가 같음을 단언한다(캐시 가능성이 있어 단독 증거로 보지 않고, 같은 JDBC URL로 재접속·앱 요청이 성공하는 것을 실제 증거로 삼는다). 데이터는 컨테이너 파일시스템에 있어 재시작 후에도 남는다.
- 타임아웃: 앱은 `hikari.connection-timeout=2000`, `maximum-pool-size=3`으로 띄워(운영 기본은 30초) 재시작 중 요청이 약 2초 안에 503으로 끝나게 한다.
  HTTP 클라이언트는 연결 5초·요청 20초 상한, 재시작 복구 폴링은 90초 상한이다.
- 완료 기준: `postgresTest` 반복 통과(`--rerun-tasks`), `spotlessApply check` 통과.

## 구현 결과와 직접 확인
- 구현: `PostgresRestartLoadTest`(태그 `postgres`, 3개). 앱 인스턴스 1개를 `SpringApplicationBuilder`로 띄워 실제 HTTP로 호출. main 코드 변경 없음.
- 시나리오와 관찰값:
  - 재시작: 접수 1건 성공 후 `restartContainerCmd`를 별도 스레드로 실행하고 그 사이 이력 조회·같은 키 접수를 50ms 간격으로 반복.
    관찰된 (이력/접수) 상태열은 실행마다 달랐다(예: `[503/200, 200/200]`, `[200/503, 503/200, 200/200]`). 매번 503이 포함됐고 500은 없었다.
    `pg_postmaster_start_time`이 재시작 후 더 늦어졌고 포트는 그대로였다. 새 사용자 흐름 정상, 이전 키 재현 동일, 접수 2건, 키-접수 시각 불일치 행 0.
  - 폭주: 1차 응답 분포 `ALREADY_REQUESTED/409=80, LIMIT_EXCESS/400=96, OK/200=80`(500·503 없음). 사용자마다 10건·합계 988.0으로 동일. 응답 200 수와 행 수 일치.
  - 풀 고갈: 풀 연결을 모두 점유한 채 접수하면 connection-timeout 뒤 503 `DB_UNAVAILABLE`(관찰 경과 2011~2025ms), 해제 후 200.
- 한계: 폭주 테스트의 풀(3)과 connection-timeout(2초)에서는 폭주 중 풀 고갈 503이 실제로 발생하지 않았다(503 재시도 경로는 코드에 있으나 실행되지 않음).
  풀 고갈은 별도 결정적 테스트로 확인했다. 재시작 중 관찰값은 타이밍에 따라 달라지므로 계약(200/503만, 복구)만 단언하고 시퀀스를 고정하지 않는다.
  커밋 도중 재시작으로 응답이 유실된 불확실 경우는 결정적으로 재현하지 못했다(같은 키 재시도로 확인해야 한다는 기존 계약만 유효).
  컨테이너 재시작이므로 PostgreSQL 프로세스 정상 종료(SIGTERM) 경로이고, 비정상 종료·네트워크 분리·장시간 부하·다른 버전은 검증하지 않았다.
